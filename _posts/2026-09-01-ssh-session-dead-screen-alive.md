- SSH로 붙어 nano로 파일을 편집하던 중, 터미널이 **입력을 전혀 받지 않는 상태**가 됐다. 그런데 화면에는 nano 편집 화면이 멀쩡하게 떠 있었다.
- 화면이 남아 있는 건 **서버가 살아 있다는 증거가 아니다.** 터미널 에뮬레이터는 마지막으로 받은 바이트까지 그려놓고 있을 뿐이고, 연결은 이미 조용히 끊겨 있었다.
- 먹통 창은 `Enter` → `~` → `.`로 강제로 끊을 수 있고, 저장 못 한 nano 버퍼는 **`<파일명>.save`** 로 남아 있을 수 있다.

---

## 1. 문제 상황

VM에 SSH로 붙어서 nano로 과제 파일을 편집하고 있었다. 그러다 어느 순간부터

- 키를 눌러도 **화면에 글자가 안 찍힌다**
- `Ctrl+O`(저장)도, `Ctrl+X`(종료)도 반응이 없다
- 그런데 **화면에는 nano 편집 화면이 그대로 떠 있다.** 에러 메시지도, "연결이 끊겼습니다" 같은 안내도 없다
- 저장 안 한 내용이 날아갈까 봐 창을 닫지도 못하고 한참 들여다봤다

제일 헷갈렸던 게 **아무 에러도 안 나온다**는 점이었다. 끊겼으면 끊겼다고 말해줄 줄 알았다.

## 2. 환경

- **호스트**: Windows, PowerShell의 OpenSSH 클라이언트
- **게스트**: VirtualBox + Ubuntu, NAT + 포트 포워딩(호스트 2222 → 게스트 22)
- 편집기: `nano`
- 확인 시점: 2026-09-01

## 3. 원인을 좁혀나간 과정

### 3-1. 오진: "VM이 멈췄다"

제일 먼저 의심한 건 VM이 뻗었다는 것이었다. 실제로 그랬다면 강제 종료하고 다시 띄우는 수밖에 없다.

**왜 틀렸나.** 확인이 1초면 끝난다. **새 터미널을 열어서 같은 주소로 붙어봤더니 멀쩡하게 접속됐다.** VM도, sshd도 살아 있었다. 죽은 건 **그 세션 하나**였다.

> 터미널이 먹통일 때 가장 먼저 할 일은 **새 창을 하나 더 여는 것**이다. 붙으면 서버 문제가 아니고, 안 붙으면 서버 문제다. 추측하기 전에 먼저 둘로 가른다.
{: .prompt-tip }

### 3-2. 화면이 남아 있는 것은 아무 증거도 아니다

여기서 짚고 넘어간 게 핵심이었다.

터미널에 보이는 nano 화면은 **서버가 지금 그리고 있는 게 아니다.** 서버가 과거에 보낸 바이트를, 내 쪽 터미널 에뮬레이터가 화면 버퍼에 그려두고 유지하고 있는 것뿐이다. 연결이 끊겨도 그 버퍼는 지워지지 않는다.

즉 화면은 **마지막 순간의 잔상**이고, 연결 상태에 대해 아무것도 말해주지 않는다. "화면이 멀쩡하니까 살아 있겠지"는 처음부터 성립하지 않는 추론이었다.

## 4. 왜 끊겼다는 말도 없이 조용히 죽는가

TCP 연결은 **양쪽이 아무 말도 안 하는 동안에는 끊겼는지 알 수 없다.** 확인하려면 뭔가를 보내보는 수밖에 없다.

```text
[정상]
  클라이언트 ──키 입력──→ sshd ──→ nano
            ←─화면 갱신──

[조용히 끊긴 뒤]
  클라이언트 ──키 입력──→  ✕ (중간에서 버려짐)
            (응답 없음, 에러도 없음)
                              sshd ──→ nano  ← 서버도 모른 채 살아 있음
```

중간 경로가 조용히 패킷을 버리는 상황은 생각보다 흔하다.

- VM을 일시정지(pause)했다가 재개한 경우
- 호스트가 절전/최대 절전에 들어갔다 깨어난 경우
- 무선 ↔ 유선 전환, IP 변경
- NAT/방화벽의 연결 추적 테이블이 유휴 시간 초과로 엔트리를 버린 경우

이 중 어느 것도 **RST를 보내주지 않는다.** 거부가 아니라 침묵이다. 그래서 클라이언트는 자기가 보낸 키 입력이 어디서 사라졌는지 모르고, OS의 TCP 재전송 타임아웃(길면 10분 이상)이 끝날 때까지 기다린다. 그 시간이 지나야 비로소 `Broken pipe`가 뜬다.

```text
client_loop: send disconnect: Broken pipe
```

서버 쪽도 마찬가지다. `ClientAliveInterval`이 설정돼 있지 않으면 sshd 역시 클라이언트가 사라진 걸 한참 모른다. 그동안 **내 셸과 nano 프로세스는 서버에서 계속 살아 있다.**

그리고 sshd가 끊김을 감지하는 순간, 그 세션의 프로세스 그룹에 **SIGHUP**을 보낸다. nano는 SIGHUP이나 SIGTERM을 받으면 수정 중이던 버퍼를 버리지 않고 **`<파일명>.save`** 라는 이름으로 저장한다. (파일명이 없는 새 버퍼였다면 `nano.save`다.)

> 원래 메모에는 "숨김파일을 찾아보라"고 적어뒀었는데, 그건 **vim 기준**이다. vim은 `.파일명.swp`라는 숨김 스왑 파일을 쓰지만, **nano는 숨김이 아닌 `파일명.save`** 다. 찾는 위치가 다르면 못 찾는다.
{: .prompt-warning }

## 5. 직접 확인하는 법

새 터미널에서 붙은 다음, 서버 쪽에 뭐가 남아 있는지 본다.

```bash
# 접속해 있는 세션 목록 — 죽은 세션이 아직 붙어 있는 것으로 보이는 경우가 많다
who
w
```

내 프로세스가 아직 돌고 있는지 본다.

```bash
ps -ef | grep -E 'nano|sshd' | grep -v grep
```

nano가 아직 살아 있다면 아직 SIGHUP이 안 간 것이고, 사라졌다면 이미 정리된 것이다. 후자라면 저장본을 찾는다.

```bash
# nano의 비상 저장본 (숨김 아님)
ls -la ~/homework/
ls -la ~/homework/*.save

cat ~/homework/과제파일.txt.save
```

## 6. 해결

### 6-1. 먹통 창 끊기

창을 그냥 닫아도 되지만, SSH 클라이언트에는 **끊기 전용 이스케이프 시퀀스**가 있다. 순서대로 누른다.

```text
Enter  →  ~  →  .
```

`~`는 줄의 맨 처음에 있을 때만 이스케이프 문자로 인식되므로, **먼저 `Enter`를 눌러 줄을 새로 시작하는 게 중요하다.** 그다음 `~`, `.` 순으로 치면 응답 없는 세션이라도 클라이언트가 즉시 연결을 끊는다. 10분짜리 TCP 타임아웃을 기다릴 필요가 없다.

(`Enter` → `~` → `?`를 누르면 쓸 수 있는 이스케이프 목록이 나온다.)

### 6-2. 남은 프로세스 정리와 복구

새 세션에서 `.save` 파일이 있으면 내용을 확인하고 원본에 덮거나, 이어서 작성한다.

```bash
cat ~/homework/과제파일.txt.save
mv ~/homework/과제파일.txt.save ~/homework/과제파일.txt
nano ~/homework/과제파일.txt
```

## 7. 재발 방지

**① tmux(또는 screen) 안에서 작업한다.** 이게 진짜 해결책이다. 세션이 끊겨도 tmux 세션은 서버에 그대로 남아 있고, 재접속해서 붙으면 **편집하던 화면 그대로** 돌아온다.

```bash
sudo apt install tmux -y

tmux new -s work      # 새 세션 시작
# (연결이 끊긴 뒤 재접속해서)
tmux attach -t work   # 하던 자리로 복귀
```

끊김을 막는 게 아니라 **끊겨도 아무 일도 아니게 만드는 것**이라서, 위의 복구 절차 전체가 필요 없어진다.

**② 클라이언트에서 keepalive를 보낸다.** 끊김을 10분이 아니라 1분 안에 알아챈다. 유휴 연결이 NAT 테이블에서 사라지는 것도 같이 막아준다.

`~/.ssh/config`에 넣어두면 매번 안 쳐도 된다.

```text
Host *
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

**③ 서버에서도 유령 세션을 정리하게 한다.** `/etc/ssh/sshd_config`에서:

```text
ClientAliveInterval 30
ClientAliveCountMax 3
```

이러면 서버가 90초 안에 끊김을 감지하고 세션을 정리한다 — nano의 `.save`도 그만큼 빨리 생긴다.

## 8. 정리

| | |
| --- | --- |
| 증상 | 입력에 아무 반응 없음, 에러도 없음, 화면은 멀쩡 |
| 메커니즘 | TCP가 조용히 끊겼고(RST 없음) 양쪽 다 모른다. 화면은 끊기기 전의 잔상 |
| 서버 쪽 | sshd가 감지할 때까지 셸·nano가 계속 살아 있다가, SIGHUP 시 `<파일명>.save`로 저장됨 |
| 해결 | `Enter ~ .`로 강제 종료 → 새 세션에서 `.save` 복구 |
| 재발 방지 | **tmux** / `ServerAliveInterval` / `ClientAliveInterval` |

**설명** — 에러가 안 뜨는 이유는, 끊김이 거부(RST)가 아니라 **침묵**이기 때문이다. 침묵은 타임아웃으로만 감지할 수 있고, keepalive를 안 켜두면 그 타임아웃이 OS 기본값(수 분~10분 이상)이다.

**예측** — 먹통 상태로 그냥 10분쯤 두면? 결국 `client_loop: send disconnect: Broken pipe`가 뜨고 창이 돌아온다. **에러는 안 나는 게 아니라 늦게 나는 것**이다.

**파괴** — VirtualBox에서 VM을 일시정지했다 1분 뒤 재개하면 이 상태를 **의도적으로 재현**할 수 있다. 같은 조건에서 tmux 안에서 작업하고 있었다면 `tmux attach` 한 번으로 아무 손실 없이 복귀한다 — 두 번 해보면 tmux를 왜 쓰는지가 몸으로 이해된다.

배운 건 두 가지다. **화면에 보이는 것은 과거다.** 그리고 터미널이 먹통일 때는 추측하지 말고 **새 창을 하나 더 열어서** 서버 문제인지 세션 문제인지부터 가른다.
