- VirtualBox VM에 SSH 포트포워딩으로 접속했는데, 타이핑 자체는 되는 것 같은데 **화면 반영이 몇 분씩 지연**됐다.
- 원인은 네트워크 속도가 아니라, **sshd가 접속한 클라이언트의 IP를 이름으로 되돌려 조회하면서 응답 없는 DNS를 타임아웃까지 기다리는 것**이었다.
- `/etc/ssh/sshd_config`에서 `UseDNS no` + `GSSAPIAuthentication no`로 해결. 다만 **둘을 동시에 껐기 때문에 어느 쪽이 범인이었는지는 확정하지 못했다** (3-2 참고).

---

## 1. 문제 상황

호스트(Windows) PowerShell에서 VirtualBox의 우분투 VM에 SSH 포트포워딩으로 접속했다.

```bash
ssh -p 2222 ubuntu@localhost
```

접속은 된다. 그런데

- 프롬프트가 뜨기까지 수십 초에서 몇 분이 걸린다
- 접속 후에도 명령을 치면 **입력은 받는 것 같은데 화면에 반영되기까지 한참 걸린다**
- 멈춘 줄 알고 기다리다 보면 그동안 입력했던 게 한꺼번에 쏟아진다

"터미널이 먹통"처럼 보이지만, 입력이 유실되지 않고 나중에 몰아서 나온다는 점이 중요한 단서였다.

## 2. 환경

- **호스트**: Windows, PowerShell에서 OpenSSH 클라이언트 사용
- **게스트**: VirtualBox + Ubuntu, 네트워크는 **NAT + 포트 포워딩**(호스트 2222 → 게스트 22)
- VM은 수업 실습용이라 외부 인터넷/DNS 접근이 보장되지 않는 상태였다
- 확인 시점: 2026-09-01

## 3. 원인을 좁혀나간 과정

### 3-1. 오진: "VM이 느려서" / "네트워크가 느려서"

처음엔 t2.micro급 VM 성능이나 포트포워딩 오버헤드를 의심했다.

**왜 틀렸나.** 느린 네트워크나 느린 CPU라면 **전반적으로 균일하게** 느려야 한다. 그런데 이 증상은

- 접속 초기에 집중되고
- 입력이 유실되지 않고 **나중에 한꺼번에 나온다**

즉 데이터가 못 가는 게 아니라, **어떤 단계가 끝날 때까지 세션이 블록돼 있는 것**이다. "느리다"와 "무언가를 기다린다"는 전혀 다른 증상이고, 후자는 거의 항상 **타임아웃**을 의심해야 한다.

### 3-2. 범인: 로그인 단계에서 응답 없는 조회를 기다린다

sshd는 클라이언트가 접속하면 로그인 처리 과정에서 외부에 뭔가를 물어보는 단계가 있다.

1. **역방향 DNS 조회(`UseDNS`)** — 접속해온 IP가 어떤 호스트명인지 거꾸로 조회한다. 로그와 `from=` 기록, `sshd_config`의 호스트명 기반 접근 제어에 쓰기 위한 것이다.
2. **GSSAPI 인증 시도(`GSSAPIAuthentication`)** — Kerberos 기반 인증을 먼저 시도한다. Kerberos 환경이 아니면 무의미하다.

둘 다 **외부 응답을 기다리는 동작**이고, DNS 서버가 응답하지 않으면 거부(refuse)가 아니라 **침묵**이라서 클라이언트는 타임아웃까지 꽉 채워 기다린다. VM이 NAT 뒤에 있고 DNS에 제대로 닿지 못하는 상태라면 이 대기가 그대로 로그인 지연으로 나타난다.

> **확정하지 못한 것**: 나는 아래 해결책에서 **두 줄을 동시에** 바꿨고, 그 뒤 증상이 사라졌다. 그래서 둘 중 어느 쪽이 실제 원인이었는지는 모른다.
>
> 그리고 한 가지 더 — OpenSSH는 **6.8 버전 이후 `UseDNS`의 기본값이 `no`**다. 우분투의 기본 `sshd_config`에도 `#UseDNS no`로 주석 처리돼 있을 뿐이라, 명시적으로 `yes`로 켜둔 게 아니라면 역방향 DNS는 애초에 돌지 않았을 가능성이 있다. 반면 **`GSSAPIAuthentication`은 우분투 기본 설정에서 `yes`로 켜져 있다.** 그렇다면 더 유력한 범인은 GSSAPI 쪽이다. 확인하지 않았으므로 추정으로 남겨둔다.
{: .prompt-warning }

## 4. 왜 침묵하는 DNS가 몇 분이 되는가

`refused`(거부)와 `timeout`(무응답)은 체감이 완전히 다르다.

```text
[응답이 거부됨]
  sshd --- 조회 ---> DNS 서버
       <-- REFUSED --      → 즉시 실패, 로그인 계속 진행 (체감 0초)

[응답이 없음]
  sshd --- 조회 ---> (허공)
       ...재시도...
       ...재시도...       → 타임아웃까지 대기, 그동안 세션 블록
```

리졸버는 보통 `/etc/resolv.conf`의 **네임서버 목록을 순서대로** 시도하고, 각각에 대해 타임아웃(기본 5초) × 재시도(기본 2회)를 반복한다. 네임서버가 여러 개 등록돼 있고 전부 무응답이면 한 번의 조회가 수십 초로 늘어난다. 로그인 과정에서 이런 조회가 여러 번 일어나면 합쳐서 분 단위가 된다.

입력이 유실되지 않고 나중에 쏟아진 이유도 같다. TCP 연결과 입력 버퍼는 멀쩡했고, **셸이 입력을 처리하기 시작하는 시점이 늦어진 것**뿐이다.

## 5. 직접 확인하는 법

클라이언트에서 verbose로 붙여서 **어느 줄에서 멈추는지**를 본다. 이게 제일 빠르다.

```bash
ssh -vvv -p 2222 ubuntu@localhost
```

출력이 `debug1: Next authentication method: gssapi-with-mic` 근처에서 오래 멈춰 있으면 GSSAPI, 인증이 끝난 뒤 세션 열기 단계에서 멈추면 DNS 쪽을 의심한다.

지연 시간을 숫자로 재두면 전/후 비교가 가능하다.

```bash
# 접속해서 바로 종료하는 데 걸리는 시간
time ssh -p 2222 ubuntu@localhost 'exit'
```

VM 안에서는 DNS가 실제로 응답하는지 본다.

```bash
cat /etc/resolv.conf

# 역방향 조회가 타임아웃되는지 (호스트에서 들어오는 IP로)
dig +short -x 10.0.2.2
time getent hosts 10.0.2.2
```

현재 적용된 sshd 설정값은 추측하지 말고 직접 출력한다.

```bash
sudo sshd -T | grep -Ei 'usedns|gssapi'
```

## 6. 해결

VM 안에서 sshd 설정을 수정한다.

```bash
sudo nano /etc/ssh/sshd_config
```

아래 두 줄을 찾아서 (없으면 추가) 이렇게 설정한다.

```text
UseDNS no
GSSAPIAuthentication no
```

저장 후 SSH 서비스를 재시작한다.

```bash
sudo systemctl restart sshd
```

> 설정을 잘못 건드린 상태로 sshd를 재시작하면 더 이상 접속하지 못할 수 있다. **지금 붙어 있는 세션은 끊지 말고**, 새 터미널에서 재접속이 되는지 확인한 다음에 기존 세션을 닫는다. 재시작 전에 `sudo sshd -t`로 문법 검사를 먼저 하면 더 안전하다.
{: .prompt-tip }

호스트에서 재접속해서 확인한다.

```bash
ssh -p 2222 ubuntu@localhost
```

## 7. 재발 방지

- 실습용 VM을 새로 만들 때마다 같은 증상이 나므로, **VM 초기 세팅 체크리스트에 이 두 줄을 넣어둔다.**
- 설정 파일을 직접 고치는 대신 drop-in 파일로 관리하면 원본을 건드리지 않아도 된다. (OpenSSH 8.2+ 에서 `Include /etc/ssh/sshd_config.d/*.conf`가 기본으로 들어 있다.)

```bash
echo -e 'UseDNS no\nGSSAPIAuthentication no' | sudo tee /etc/ssh/sshd_config.d/99-no-lookup.conf
sudo sshd -t && sudo systemctl restart sshd
```

- **다음엔 한 번에 한 줄만 바꾼다.** 이번에 어느 쪽이 범인인지 모르게 된 이유가 이거다.

## 8. 정리

| | |
| --- | --- |
| 증상 | SSH 접속·입력 반영이 수십 초~수 분 지연. 입력은 유실되지 않고 나중에 몰아서 나옴 |
| 메커니즘 | 로그인 단계의 외부 조회(역방향 DNS / GSSAPI)가 **무응답 타임아웃**을 끝까지 기다림 |
| 근본 원인 | **미확정.** 두 줄을 동시에 껐다. 기본값을 보면 `GSSAPIAuthentication`이 더 유력 |
| 해결 | `UseDNS no`, `GSSAPIAuthentication no` + `systemctl restart sshd` |
| 재발 방지 | VM 초기 세팅 체크리스트 / drop-in 파일 / **변수 하나씩 바꾸기** |

**설명** — 입력이 유실되지 않고 나중에 쏟아졌다는 건 전송이 아니라 **처리 시작 시점**이 늦었다는 뜻이다. 그래서 "느린 네트워크"가 아니라 "대기 중인 무언가"를 찾아야 했다.

**예측** — 같은 VM에서 `UseDNS`만 끄고 `GSSAPIAuthentication`은 켜둔 채 재접속하면? 우분투 기본값 기준으로는 **여전히 느릴 것이다.** 이걸 해보면 3-2에서 미확정으로 남긴 것이 확정된다.

**파괴** — `/etc/resolv.conf`의 네임서버를 응답하지 않는 주소(`192.0.2.1` 같은)로 바꾸고 `UseDNS yes`를 명시하면 증상을 **의도적으로 재현**할 수 있다. 재현할 수 있으면 원인을 확정할 수 있다.

가장 크게 배운 건 "느리다"와 "기다린다"를 구분하는 것이었다. 전자는 성능 문제고 후자는 거의 항상 타임아웃이다. 그리고 **고칠 때 변수를 하나만 바꿔야 한다**는 것 — 두 개를 같이 바꾸면 증상은 사라지지만 배우는 건 없다.
